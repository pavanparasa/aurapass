# AuraPass browser extensions

Chromium and Firefox extensions that fill logins and one-time codes from a local
AuraPass vault. Both share one implementation; only the manifest differs.

## How it fits together

```
  ┌──────────────┐   plaintext JSON over one   ┌───────────────────────┐
  │ popup /      │   encrypted WebSocket       │ AuraPass desktop app   │
  │ content.js   │◀───────────────────────────▶│   or aurapass-bridge   │
  └──────┬───────┘                             └───────────────────────┘
         │ runtime.sendMessage                       ws://127.0.0.1:8974
  ┌──────▼───────┐
  │ background.js│  the only place that holds the pairing token
  └──────────────┘
```

* `shared/lib/crypto.js` — XChaCha20-Poly1305, HChaCha20, Poly1305 (WebCrypto for
  SHA-256/HMAC/HKDF). Checked against the RFC 8439 and
  draft-irtf-cfrg-xchacha-03 vectors by `tools/test-crypto.mjs`.
* `shared/lib/bridge.js` — the bridge client: pairing handshake, sealed
  request/response, typed helpers (`status`, `matchUrl`, `item`, `totp`, …).
* `shared/lib/ext.js` — Chrome/Firefox API shims, settings storage, helpers.
* `shared/background.js` — the worker. Owns the socket and the token; answers
  every request from the popup and the content script.
* `shared/content.js` — finds login forms, shows the match dropdown, fills with
  the native setters, offers to save a submitted login.
* `shared/popup.*`, `shared/options.*` — the toolbar popup and the settings page.
* `shared/icons/*.png` — generated by `tools/make-icons.mjs`.

The page never talks to the bridge and never sees the token; the content script
asks the background for matches and only receives a decrypted password after the
user picks one.

## Building

```sh
./extensions/build.sh          # copy shared/ into chromium/ and firefox/, validate
./extensions/build.sh --test   # also run the crypto test vectors
./extensions/build.sh --zip    # also write the distributable packages
```

`--zip` writes three things per browser:

| file | what it is | used for |
| --- | --- | --- |
| `aurapass-chromium-1.0.0.zip` | the extension folder, zipped | *Load unpacked* after unzipping, Chrome Web Store upload |
| `aurapass-chromium-1.0.0.crx` | CRX3 container signed by `packaging/keys/aurapass-chromium.pem` | enterprise policy deployments and archives — **not** double-click installable (Chrome answers `CRX_REQUIRED_PROOF_MISSING`) |
| `aurapass-firefox-1.0.0.xpi` | the same zip with the name Firefox expects | `web-ext sign`, AMO, Developer Edition/Nightly installs |

The CRX is produced by `packaging/pack-crx.py`, a small dependency-free
implementation of the documented CRX3 format, because Chrome's own
`--pack-extension` cannot write outside its sandbox when Chrome is installed as
a Flatpak. Keep the key: the extension id (`oeppnfkipchjgnoipmmmaeameknhegij`)
and therefore every future update derive from it.

The Chrome Web Store wants the **zip** and re-signs it itself; AMO wants the
**xpi** (or the zip) and signs it. See `STORE.md` for the listing copy,
permission justifications and the privacy questionnaire.

`shared/` is the source of truth. `chromium/` and `firefox/` are build outputs
plus a checked-in `manifest.json`; never edit the copies there.

## Installing

**Chromium / Chrome / Brave / Edge**

1. `./extensions/build.sh`
2. Open `chrome://extensions`, enable Developer mode.
3. *Load unpacked* → pick `extensions/chromium` (the `.deb` puts the same
   folder at `/usr/share/aurapass/extensions/chromium`). Flatpak Chrome cannot
   read `/usr/share`, so copy it into your home first:
   `cp -r /usr/share/aurapass/extensions/chromium ~/.local/share/aurapass-chromium`.

A `.crx` cannot be installed by dragging it into Chrome any more; Chrome only
accepts one from the Web Store or through enterprise policy. Use *Load
unpacked* for local installs, or publish the zip.

**Firefox**

1. `./extensions/build.sh`
2. Open `about:debugging#/runtime/this-firefox`.
3. *Load Temporary Add-on* → pick `extensions/firefox/manifest.json` (or the
   `.xpi`). This lasts until Firefox restarts, and Firefox treats it as
   removed when it exits — so it can forget the browser's pairing too. Expect
   to approve the browser again after a restart. Installing a signed `.xpi`
   permanently avoids that.

If AuraPass is reinstalled or its configuration is reset, an old approval can
become invalid. The extension now detects that, clears the dead secret and
asks for approval once more when you click its toolbar button.

Firefox release builds only install signed add-ons permanently. To keep it,
either sign the `.xpi` with `web-ext sign` (a free AMO account; it can stay
unlisted), or use Developer Edition/Nightly with
`about:config` → `xpinstall.signatures.required = false` and open the `.xpi`.

## Pairing

1. Start AuraPass and unlock the vault.
2. Click the AuraPass button in the browser toolbar.
3. The desktop app asks *“Chrome wants to connect”*. Click **Allow**.

That is the whole flow. No address is shown, no token is copied, and the
extension stores the secret the app issues behind the scenes. Revoke a browser
at any time in **AuraPass → Settings → Browser extension**.

Once a browser is approved, clicking the toolbar button opens AuraPass's own
quick assistant, centred on the screen as a compact 400×450 panel, and closes
the browser pop-up.

Headless machines can still pair manually: `aurapass-bridge --print-token`.

## Security model

| Threat | Mitigation |
|---|---|
| A website reading the vault | content scripts never hold the token or talk to the bridge; they ask the background and receive one item at a time |
| Another local user on the port | only a browser the user explicitly approved is issued a secret; it authenticates the handshake, and every frame is XChaCha20-Poly1305 sealed |
| A browser asking for access behind the user's back | pairing needs a click in the desktop app, which names the browser and can be declined; unapproved browsers get no key and no data |
| Network attacker | the bridge binds `127.0.0.1` only |
| A stolen token | the token still only unlocks a locked vault when the desktop app allows remote unlock |
| Credentials in the DOM | filled values live in the page's fields, as any password manager's do |

## Testing

```sh
node extensions/tools/test-crypto.mjs                       # RFC vectors
node extensions/tools/test-bridge.mjs --token <t> --port <p> # live interop
```

`test-bridge.mjs` drives a real `aurapass-bridge` with the same client the
extension uses, and covers every request the popup can make.
